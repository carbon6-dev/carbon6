# Analytics — Design

Status: built (2026-10-23). A first step toward docs/measurement.md: the measures carbon6 can take from its own logs, with nothing asked of you. Outcomes, value and leverage are still deferred.

## 1. What it shows

**Analytics** in the header opens the page in a tile. For the last day, 7, 30 or 90 days, and only for sessions with the label filter's labels, it shows:

- **Agent time:** from each finished turn's start to its end, summed over sessions and subagents. It splits into:
  - **model time:** waiting on model responses, measured from the event before each call to its usage;
  - **tool time:** tools' own durations (parallel calls each count);
  - **other:** everything else in the turn (hooks, approvals, the worker's own work).
- **Agents at once:** the most turns running at the same moment on a day.
- **You:**
  - your messages, split into **new tasks** (a session's first message) and **corrections** (later messages, interrupts and rewinds);
  - **answers** to approvals and questions;
  - **agent time per message of yours,** a rough measure of how far each message carries.
- **Waiting on you:** how long a finished turn waited for your reply, and an approval or question for your answer (median and 90th percentile). This is what to shorten to get more done.
- **Cost and tokens,** from the usage table at today's prices (Settings → Prices).
- **By model:** time, calls, time per call, output tokens per second of model time, tokens, cost.
- **By tool:** time, calls, median duration, share failed.
- **By a label key you pick** (`repo` at first; any key, like `client`): agent time, sessions, turns, your messages, corrections per task, cost.

Each day chart has a hover readout per day and a table.

## 2. How

- **Marks.** As each event is stored, the head writes a timing mark to the `activity` table for events that say who was working: your message, turn start and end (with its reason), model call (usage, with the model), tool result (tool, its duration, failed), approval and question states, rewind. Events stored before the table existed are marked once at startup (`activity_backfilled`).
- **The report** (`GET /api/v1/analytics?days=&labels=&by=`) walks the marks of the range per session in order. It also reads a day before the range, for turns already under way. Then it adds the `usage` table's calls. Model and tool time count when their turn ends, like agent time, so a running turn doesn't count yet.
- **Not measured:** your time in carbon6 or elsewhere (presence, docs/measurement.md §7), and whether the work was kept (outcomes). "Waiting on you" includes nights and weekends: read the median, not the sum.

## 3. API

`GET /api/v1/analytics` (operation `usage.analytics`) returns `AnalyticsReport`:

- `total`, `by_day` (every day of the range), `by_model`, `by_group` (values of the label key `by`; `""`: sessions without it): rows of `ActivityRow`;
- `by_tool`;
- `waits`;
- `unpriced_models`.

## 4. Plan limits

Subscriptions have usage windows rather than prices: a Claude Code subscription (5 hours, the week, a model's week, overage) and a ChatGPT plan (a short window and the week). carbon6 shows how much of each is left and when it starts afresh. The API's `used_percent` is unchanged; only presentation converts it to percent left:

- **Where:** in the message box, the model chip ends with the tightest window's share left ("opus · high · 90% left"; its hover: "Week: 90% left · resets Sun Nov 8, 9:00 am"), and its menu starts with a **Usage** section: a row per window with a bar of what's left, "N% left", and when it resets in your local time ("today 3:40 pm", "tomorrow 9:00 am", "Sun Nov 8, 9:00 am"). Under each such connection in Settings → Connections (a bar per window: "5-hour: 66% left · resets today 3:40 pm"), in **Plan limits** on the Usage page, and wherever you pick a connection (a side chat's model picker, the new-session form): each option reads "name · 90% left", and the chosen one shows "90% left" beside the picker. Text and bars consistently show what remains; exhausted windows say **used up**. The colour goes by what's left: grey over 50%, yellow from 50%, amber from 20% (or when the provider warns), red under 5% (or when used up).
- **Claude Code** reports its subscription's windows itself as its sessions run (`rate_limit_event` in its stream: `unifiedWindows` with each window's utilization, reset time and status). The worker passes each report to the head (`EphemeralEvent.rate_limit`), which keeps it for the session's connection. It costs nothing and is as fresh as the last turn on that connection; a report about one window keeps the others.
- **ChatGPT plans** come from rate-limit headers on model replies to the head (suggestions, session names, catch-up, Ask, and ChatGPT members of pools), using the same OAuth sign-in as the model call. The headers are `x-codex-primary-used-percent`, `x-codex-primary-window-minutes`, `x-codex-primary-reset-at` and the corresponding `secondary` headers: percentages used, window lengths in **minutes**, resets as **Unix seconds**. These names and units follow Codex's `codex-rs/codex-api/src/rate_limits.rs` and `codex-rs/protocol/src/protocol.rs` (`RateLimitWindow`). The head names windows by length (e.g. 300 minutes → `5h`, 10080 → `week`), merges partial reports and clears any earlier read error. No extra request is needed. The old usage endpoint (`https://chatgpt.com/backend-api/wham/usage`; head setting `chatgpt_usage_url` for a stand-in or proxy) remains a fallback every 3 minutes and after stale turns, only until headers arrive or it answers `rejected_by_access_enforcement`: carbon6's OAuth app cannot read that endpoint. That refusal is logged once per connection per head run, stops further polling and is not a plan-limit error.
- **ChatGPT diagnostics** (INFO): the first successful plan response with no usable `x-codex` usage snapshot logs `ChatGPT reply has no usable x-codex usage headers`, once per process, with `limits_hook_installed` and filtered `header_names` (containing `codex`, `rate`, `limit`, `usage`, `quota`, or starting with `x-`). These are **names only, never values**. The first snapshot recorded for each connection logs `ChatGPT plan limits from reply headers: 5h, week` (the actual window names), once per connection per process, with no token or account data. The missing-header diagnostic runs even without a hook, so its flag distinguishes absent headers from a client not wired to record them.
- **API keys and local servers** have no plan limits: their spend is the Usage page's, against budgets.
- **Local Codex fallback (opt-in per worker):** on the console's **Workers** page, under **ChatGPT plan limits**, check the machine with a signed-in Codex CLI. No worker is enabled by default. The head setting `codex_limits` is `{"workers":["<worker id>"],"commands":{"<worker id>":"/absolute/path/to/codex"}}`, read/set with `GET`/`PUT /api/v1/settings/codex_limits` (`workers.codex_limits.get`/`.put`, administration only). The `commands` map is optional and defaults to empty for existing settings; no migration is needed. Each worker has an optional **Codex command** input beside its checkbox: an absolute executable path, without arguments or `~` expansion, overrides discovery. Clear it to discover automatically. Workers check the setting within 30 seconds, read once when enabled/attached or the command changes (even during error backoff), then every 5 minutes; failures back off from 10 minutes to an hour. Disabling stops future reads; last observations remain as history.
  - **Discovery uses the user's shell, not hard-coded installation locations.** With no override, runs `$SHELL -lic 'command -v codex'` once (or `/bin/sh -lc` if `SHELL` is unset/empty). Stdin is closed; stderr and banner noise are ignored; only the last absolute-path line of bounded stdout is accepted. The shell has a 5-second timeout and bounded process-group cleanup. The result is cached in this worker poller; it is resolved again only after a failed read/discovery or a setting change. The Workers UI shows the selected path with **from user's shell** (or **manual override**). Shell output is never imported into the worker's environment or included in diagnostics.
  - Runs the selected executable with `app-server --listen stdio://`. Its logical folder (not a symlink's canonical target folder) is prepended to this child command's `PATH`, so `#!/usr/bin/env node` finds a sibling `node`. No shell or argument expansion is used for the Codex command; the worker environment and other commands are unaffected. It runs as the service user with unchanged `HOME` and `CODEX_HOME`. It sends newline-delimited JSON-RPC `initialize` (carbon6 client name/version), waits for its answer, then `initialized` and `account/rateLimits/read` with `excludeResetCreditDetails: true`. Invalid Request (`-32600`, used by Codex's request deserializer) or Invalid Params (`-32602`) retries once without params; authentication/network errors do not. Then `account/read` with `refreshToken: false` gets the signed-in ChatGPT account's `email` and `planType` (`GetAccountParams`, `GetAccountResponse.account`, `Account::Chatgpt` in `codex-rs/app-server-protocol/src/protocol/v2/account.rs`; verified at Codex commit `9fcaeb733522adf09b4e1c594bc90f344374a926`, method mapping in `protocol/common.rs`). An unsupported `account/read` can still match by account id. Each exchange has a 10-second timeout; stdin is closed, the process reaped (terminated if necessary), and stdout/stderr drained with bounded cleanup. No model turn, token read, credential copy, `auth.json` access, or keyring access is involved. Missing binaries show **Codex not found: set its path**, including beside the worker's path input. Malformed responses, missing sign-in and timeouts also produce quiet, bounded worker diagnostics; raw CLI output is never logged or reported.
  - Additive **HeadCall** methods, with no protobuf or protocol-version change: `quotas.codex.config {}` returns `{"enabled":bool,"command":string|null}` for the authenticated worker; `quotas.codex.report` sends `{observed_at, account_id, email, plan_type, command, command_from_shell, windows:[{used_percent, window_minutes, resets_at}], error}`. New fields default for older workers/saved observations. Observation times are Unix milliseconds; resets are Unix seconds on this worker-to-head call. The head checks opt-in again and supplies worker identity itself. Both `rateLimits` and `rateLimitsByLimitId["codex"]` are accepted (the latter preferred). Windows are named by duration, never primary/secondary order; percentages from Codex are rounded integers.
  - **Attribution:** first, exact nonempty account id against the connection's saved verified `workspace` (`chatgpt_account_id`); all connections for that id get the snapshot. If no id matches, compare the full emails case-insensitively: **exactly one** matching ChatGPT connection gets it. More than one is ambiguous and stays unmatched; no match stays unmatched. Never infer from a display name, plan type, partial email, email alias, or merely the existence of one connection. The verified email is already saved in the encrypted `ChatGptTokens.email` JSON and preserved on refresh; no migration/reconfiguration is needed for those connections. `workspace` comes only from the optional ID-token claim `https://api.openai.com/auth` → `chatgpt_account_id`; without it, workspace is empty, so the former id-only matcher could never match. The reported email is transient matching data, not serialized into the quota API or saved quota history.
  - Matched windows flow through the same saved quota path as headers and appear under their connection in Settings → Connections, on Usage, and in the model chip/menu. **One Codex install reports one signed-in account; other ChatGPT accounts get no numbers this way.** Unmatched snapshots remain separately under `connection_id: "codex-cli:<worker id>"` and get their own row **inside the LLM connections list**, labeled **Codex on worker · account short-id, matches no connection**, with the reason (missing ids/emails, different emails, or ambiguity), never between the add/sign-in forms. They never populate another connection's picker or send that connection's quota notifications. Read failures appear there too and retain last good windows. On the first unmatched observation per worker (reset after a match), the head logs the reason and comparisons with ids truncated to 8 characters and emails masked as `a***@domain`, never full values or connection display names.
  - Matching snapshots use the same recording, thresholds, notifications and `quotas_last` persistence as reply headers, with source `codex-cli`. Optional `origin` on each quota and window holds `source`, `observed_at`, head-supplied `worker_id`/`worker_name`, `account_id` and `plan_type`; old saved snapshots still load. Windows merge individually by observation time, newest wins, preserving the other source's unreported windows and provenance. Header windows use source `chatgpt`; Codex windows show a small **via Codex on worker** note. Worker clocks should be synchronized with the head (future timestamps are capped at receipt time).
- **Notifications** (event `quota`, on by default): when a window has 20% or less left, then 5% or less, and when it is used up, once per window and level until the window starts afresh. The title reports the percentage left; the thresholds are unchanged.
- **API:** `GET /api/v1/connections/quotas` (`connections.quotas`): `ConnectionQuota` per connection (`source`, `windows` of `QuotaWindow`: `name`, `used_percent`, `resets_at` in milliseconds, `status` allowed / warning / rejected; `updated_at`; `error`). Kept in the head's memory and saved in `quotas_last` at most once a minute (with a trailing save for newer reports), then restored after a restart until a fresh report arrives.
- **Not yet:** ChatGPT sessions on workers do not forward response headers to the head. Without a local Codex opt-in or usable headers on a head-side call, numbers may be absent or old. Codex transport, account attribution, header parsing, merging and the head's quota API are tested against stand-ins, not a live ChatGPT account. Older Codex versions that omit account ids deliberately remain unattributed. Claude Code's report was checked against Claude Code 2.1.314.
